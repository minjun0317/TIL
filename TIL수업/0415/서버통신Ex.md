# 서버통신
➡️ 내 폰(앱)이 서버한테 요청하고  
➡️ 서버가 처리해서 결과를 보내주는 과정  

= 데이터 주고받기  

Ex) 유튜브 영상 불러오기, 배달앱 주문 조회

### 특징
➡️ 서버는 눈에 안 보임  
➡️ 클라이언트 ↔ 서버 구조  
➡️ 비동기 처리 많이 사용  
➡️ 요청 / 응답 기반

---

.

.

.

# 서버
➡️ DB 데이터를 가져와서  
➡️ 처리하고 결과를 만들어주는 역할  

---

### 구조 느낌 (배달앱)
➡️ 클라이언트 = 주문 화면  
➡️ 서버 = 주문 처리 시스템  
➡️ DB = 주문/메뉴 저장소  

---

### 흐름
➡️ 주문 요청  
➡️ 서버 처리  
➡️ DB 조회  
➡️ 결과 반환

.

.

# DB (데이터 베이스)
➡️ 데이터를 저장하는 공간  
➡️ 기준(구조)을 만들어서 정리하는 곳  

DB 없으면?  
➡️ 데이터 저장 안됨 (앱 종료 시 날아감)

---

### ⬇️ 기준 없이 저장
||||
|:---:|:---:|:---:|
| 박거인 | 여자 |비둘기사랑남|
| 남자 | 옥닭발 |남자|

➡️ 의미 파악 불가  

---

### ⬇️ 기준 만들면
| 이름 | 성별 |
|:---|---:|
| 박거인 | 남자 |
| 옥닭발 | 여자 |
| 비둘기 사랑남 | 남자 |
➡️ 데이터 의미 생김  

---

### 1. 연관성
➡️ 시간 / 사용자 / 위치 기준으로 데이터 연결  
➡️ 행동 흐름 분석 가능  

---

### 2. 고유 데이터 (ID)
> GanadiA : 생성 완료  
> GanadiB : 셍상 완료  

➡️ 누가 누군지 구분 불가 

➡️ ID 필요  

Ex)  
➡️ ganadi_id = 101 → 사람A  
➡️ ganadi_id = 102 → 사람B  

➡️ 데이터 구분 가능  

---

### 핵심
➡️ DB = 저장  
➡️ 구조 필요  
➡️ ID로 구분  

---

### Q. 서버 없이 채팅 구현 가능?
➡️ 가능  

➡️ 화면만 채팅처럼 보이게 가능  
➡️ 실제 데이터 공유 / 저장 없음  

= 테스트 UI 수준  

---

➡️ 모든 것은 데이터  
➡️ DB는 그걸 정리해서 저장

# 동기
➡️ 결과 올 때까지 기다림  
➡️ 다음 작업 진행 불가  

**[동기 = 순차 처리]**

### 특징
➡️ 순서 중요  
➡️ 대기 발생  
➡️ 간단 작업에 사용

.

.

# 비동기
