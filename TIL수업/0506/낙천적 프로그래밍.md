# 낙천적 프로그래밍

→ 낙천적 프로그래밍은 서버 요청이 성공할 것이라고 예상하고, 서버 응답을 기다리기 전에 먼저 UI를 바꾸는 방식이다.

일반적으로 서버통신은 요청을 보내고 응답을 받은 뒤 화면을 바꾼다.  
하지만 낙천적 프로그래밍은 반대로, 화면을 먼저 바꾸고 서버 결과를 나중에 확인한다.

```txt
일반 방식
사용자 행동
↓
서버 요청
↓
서버 응답 대기
↓
UI 변경
```

```txt
낙천적 방식
사용자 행동
↓
UI 즉시 변경
↓
서버 요청
↓
성공하면 유지
↓
실패하면 원래대로 복구
```

## 왜 사용하는가

→ 사용자는 앱이 실제로 빠른지보다, 빠르게 반응한다고 느끼는 것을 더 중요하게 생각한다.

좋아요 버튼을 눌렀는데 서버 응답을 기다리느라 2초 뒤에 하트가 바뀌면 앱이 느려 보인다.  
하지만 버튼을 누르자마자 하트가 바뀌면 서버가 뒤에서 처리 중이어도 사용자는 빠르다고 느낀다.

## 가나디 예시

→ 가나디 게시글에 좋아요를 누르는 상황

### 일반 서버통신 방식

```txt
가나디가 좋아요 클릭
↓
서버에 좋아요 요청
↓
서버 응답 기다림
↓
성공 응답 받음
↓
하트 색 변경
```

### 낙천적 프로그래밍 방식

```txt
가나디가 좋아요 클릭
↓
하트 색 바로 변경
↓
서버에 좋아요 요청
↓
성공하면 그대로 유지
↓
실패하면 하트 색 원래대로 복구
```

## 핵심 개념

| 개념 | 설명 |
|---|---|
| Local Update | 서버 응답 전에 내 앱 안에서 먼저 UI를 바꾸는 것 |
| Request | 서버에 데이터를 보내는 요청 |
| Response | 서버가 다시 보내주는 응답 |
| Rollback | 실패했을 때 이전 상태로 되돌리는 것 |
| UX | 사용자가 앱을 사용하면서 느끼는 경험 |

## Swift 예시

```swift
final class GanadiLikeViewModel: ObservableObject {
    
    @Published var isLiked: Bool = false
    @Published var likeCount: Int = 10
    
    func tapLikeButton() {
        let previousLiked = isLiked
        let previousCount = likeCount
        
        isLiked.toggle()
        likeCount += isLiked ? 1 : -1
        
        sendLikeRequest { success in
            if !success {
                self.isLiked = previousLiked
                self.likeCount = previousCount
            }
        }
    }
    
    private func sendLikeRequest(completion: @escaping (Bool) -> Void) {
        completion(true)
    }
}
```

## 코드 흐름

| 코드 | 의미 |
|---|---|
| previousLiked | 실패했을 때 되돌리기 위한 이전 좋아요 상태 |
| previousCount | 실패했을 때 되돌리기 위한 이전 좋아요 수 |
| isLiked.toggle() | UI를 먼저 바꿈 |
| sendLikeRequest | 서버에 실제 요청 |
| if !success | 서버 요청 실패 확인 |
| Rollback | 실패 시 이전 값으로 복구 |

## 낙천적 프로그래밍을 쓰기 좋은 경우

| 상황 | 이유 |
|---|---|
| 좋아요 | 실패 확률이 낮고 UI 반응이 중요함 |
| 북마크 | 즉시 저장된 것처럼 보여주는 게 자연스러움 |
| 팔로우 | 버튼 반응이 빨라야 사용자가 답답하지 않음 |
| 체크박스 | 서버보다 화면 반응이 먼저 보여야 함 |
| 간단한 상태 변경 | 데이터 위험도가 낮으면 사용 가능 |

## 조심해야 하는 경우

| 상황 | 이유 |
|---|---|
| 결제 | 실패하면 큰 문제가 생김 |
| 회원 탈퇴 | 되돌리기 어려움 |
| 중요한 데이터 삭제 | 서버 성공 확인이 먼저 필요함 |
| 권한 변경 | 보안 문제가 생길 수 있음 |
| 점수 저장 | 서버와 값이 어긋나면 문제 발생 |

## 장점과 단점

| 구분 | 내용 |
|---|---|
| 장점 | 앱이 빠르게 느껴진다 |
| 장점 | 사용자가 기다리는 시간이 줄어든다 |
| 장점 | 좋아요, 북마크 같은 기능에 적합하다 |
| 단점 | 실패했을 때 Rollback 처리가 필요하다 |
| 단점 | 서버 데이터와 화면 데이터가 잠깐 다를 수 있다 |
| 단점 | 중요한 데이터에는 함부로 쓰면 안 된다 |

## 낙천적 프로그래밍 한줄 정리

```txt
낙천적 프로그래밍
→ 서버가 성공할 것이라 예상하고 UI를 먼저 바꾼 뒤, 실패하면 되돌리는 방식
```
