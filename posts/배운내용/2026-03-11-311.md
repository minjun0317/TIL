**Git하고 GithuB는 서로 다르다**<hr>
-
<span style="color:red">Git</span>과 <span style="color:skyblue">GithuB</span>는 문서 수정 기록을 관리하는 프로그램과 그문서를 저장하는 구글 드라이브 느낌 이라고 할 수 있다


**Git**<hr>
-
분산형 버전관리 시스템 
= 최신 버전을 관리하는 시스템, 여러사람이 동시에 개발할 때 코드를 쉽고 편리하게 관리할 수 있음

개인PC = local : 내 PC에 있는 코드 <span style="color:orange">**_Ex)한글이라는 프로그램을 사용한 최종문서 작성파일_**</span>
중앙PC = 원격 : GithuB 같은 서버에 있는 코드 <span style="color:orange">**_Ex)한글이라는 프로그램을 만든 본사에 서버_**</span>


**작동과정**<hr>
-
분산형 버전관리 시스템 : Gthub에 올린 코드는 수정할 수 없으므로 복사본을 올린다. 그리고 그 복사본을 다시 다운로드 받는다

->Git이 그걸 해줌
*
<span style="color:red">Local → Git → GitHub → 다른 사람 Local</span>


**예시구조**<hr>
-
*
시우 PC (Local) 복사본
      ↓
   GitHub (원격) 복사본
      ↓
물결 PC (Local) 복사본의 복사본



**Git-Flow(개발흐름)**<hr>
-
분산형 관리 시스템의 흐름 
 = main서버에서 패치하기 전 dev에서 코드 작업 후 빌드(작동)가 될 시 main서버의 업그레이드 버전에 적용 
*
main(상용서버) : 실제 사용자들이 사용하는 서버
*
dev(테스트 서버) : 개발 및 테스트를 하는 서버
*
branch : 같은 프로젝트 코드에서 갈라져 나온 별도의 개발 라인 즉, 원본 코드에 영향을 주지 않고 새로운 기능을 개발하거나 수정할 수 있는 독립적인 작업 공간 여기서도 dev를 팔 수 있음, 독립적으로 수정할 수 있는 코드파일을 담은 저장소


*
main (상용 서버)
       ↑ merge 
   dev (테스트 서버)
       ↑ merge -> <span style="color:red">(합병) = branch의 코드를 다른 branch로 보내는 것</span>
   branch (기능) : <span style="color:red">branch로 오류 및 수정 후 다시 테스트를 거쳐 다시 main으로</span>
       ↑
   dev (테스트 서버) : <span style="color:red">dev에서 새로운 기능을 위해 branch 생성</span>


**Pull Request(리뷰)**<hr>
-
<span style="color:red">dev</span>에서 <span style="color:skyblue">merge</span> 하기 전에 받는 승인, 검증(리뷰) 받는 행동

1. 개발자가 merge 요청
2. 팀원이 Pull Request(리뷰)
3. 승인 후 merge 진행
-> 코드 오류 방지


**Git 명령어**<hr>
-
기본 개념
*
git add
→ 변경된 파일을 git commit에 올림 (선택하는 단계)
*
git commit
→파일들을 하나의 기록으로 저장 (commit stage에 저장됨)
*
git push
→ 로컬 저장소의 커밋을 원격 저장소(GitHub)로 업로드
*
git pull
→ 원격 저장소의 최신 내용을 가져와서 로컬과 합체
